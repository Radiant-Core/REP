## Abstract

Defines an OPTIONAL `voxel_payload` field on the REP-3005 `game_item_v1` profile, allowing a Glyph game item to carry a sparse voxel geometry payload. Any REP-3017-aware client can render the item's voxel form consistently across games, marketplaces, and wallets. Clients that do not implement REP-3017 ignore the field and fall back to the standard REP-3005 preview thumbnail.

## Motivation

REP-3005 standardized on-chain game items but said nothing about *what the item looks like* beyond a 2D preview thumbnail. For voxel-class games (Minecraft / Roblox style), the most important visual attribute of a player-designed item or build is its 3D voxel geometry. Without a standard for that geometry:

- Items designed in one game cannot be rendered in another without proprietary conversion
- Marketplaces can only show a static thumbnail, killing in-context preview
- User-created builds (entire structures, vehicles, furniture, etc.) cannot be represented at all under REP-3005, which targets equipment slots

`voxel_payload` closes this gap. A creator in one voxel game inscribes a sword they designed; the same Glyph NFT, opened in any other Glyph-aware voxel game, renders the same sword. Marketplaces and wallets can show a real 3D preview.

## Specification

### Compatibility

This extension inherits Glyphs v2 envelope rules and REP-3005 game_item_v1 structure. The `voxel_payload` field SHALL be placed at `app.data.voxel_payload`, alongside REP-3005's `base` and `state` siblings.

`voxel_payload` is OPTIONAL. A `game_item_v1` Glyph without `voxel_payload` remains fully valid REP-3005. A client that does not recognize `voxel_payload` MUST ignore the field and fall back to the REP-3005 `preview` thumbnail.

### Required Fields

`voxel_payload` MUST be an object containing:

- `version` (uint): currently `1`. Future REPs MAY define `version: 2+`.
- `bounds` (map): the integer extents of the voxel volume.
  - `w` (uint): width along x, 1 ≤ w ≤ 64
  - `h` (uint): height along y, 1 ≤ h ≤ 64
  - `d` (uint): depth along z, 1 ≤ d ≤ 64
- `voxels` (array): sparse list of non-air voxels. 1 ≤ length ≤ 65,536. Each entry is a map:
  - `x` (uint): 0 ≤ x < w
  - `y` (uint): 0 ≤ y < h
  - `z` (uint): 0 ≤ z < d
  - `block` (uint): block identifier, resolved against `block_palette` if present, otherwise interpreted as a client-defined stock block id

### Optional Fields

- `origin` (array of 3 int32): `[ox, oy, oz]` placement offset for engines that snap geometry into a world. Defaults to `[0, 0, 0]`.
- `rotation` (uint): `0 | 1 | 2 | 3`, quarter-turn rotations around the Y (up) axis, applied at render time. Defaults to `0`. Engines that need finer rotation MAY interpret this as the canonical placement, then allow user overrides locally.
- `block_palette` (map of uint → text): maps the `block` ids used in `voxels` to stable cross-engine names OR Glyph ids of on-chain block-NFTs. Names follow `namespace:identifier` form (e.g. `rxd.stock:grass`, `rxd.stock:glowstone`, or `glyph:0x…` for an NFT block). Engines SHOULD resolve unknown names to a sensible fallback (e.g. a default "missing block" material).
- `textures` (array of texture refs): inline or referenced texture pointers for engines that support per-voxel texturing. Each entry:
  - `id` (uint): handle referenced by an extended voxel record (see "Extended Voxel Record" below)
  - `uri` (text): `ipfs://…`, `ar://…`, or `data:` URI
  - `hash` (map): `{ "algo": "sha256" | "blake3", "hex": <hex> }`

### Extended Voxel Record (optional)

When a `voxels` entry carries per-voxel data beyond a block id, the entry MAY include:

- `tex` (uint, optional): index into `textures[]`
- `tint` (uint, optional): 0x00RRGGBB linear color tint applied multiplicatively
- `meta` (map, optional): up to 8 small string keys, each value ≤ 32 bytes — for app-specific per-voxel state (e.g. wire signal id, item-frame contents). Engines MAY ignore unknown keys.

### Size and Cost Constraints

To keep on-chain payloads viable at the Radiant V2 fee floor (10,000 photons/byte):

- A CBOR-encoded `voxel_payload` SHOULD remain ≤ 4 KB to fit comfortably inline in a single Glyph reveal transaction
- Payloads > 4 KB SHOULD be stored externally (IPFS, Arweave) and referenced via a `content.files[]` entry whose `path` is `voxel_payload.cbor` (see REP-3005 content schema)
- Engines MUST treat externally-referenced payloads identically once dereferenced

For very large builds (entire structures, plot exports), creators SHOULD use Arweave for permanence and reference the URI from a single primary file rather than inlining.

### External Payload Form

When `voxel_payload` is stored externally, the on-chain CBOR MAY contain a placeholder marker:

```json
{
  "voxel_payload": {
    "version": 1,
    "external": {
      "uri": "ipfs://bafy.../voxel.cbor",
      "hash": { "algo": "sha256", "hex": "…" },
      "size": 12345
    }
  }
}
```

The dereferenced external file MUST be a CBOR-encoded object matching the full inline schema above, including all `required` fields.

### Mutability

If the parent Glyph has `mutable.allowed=true` and the controller's mutation policy permits, `voxel_payload` MAY be updated (e.g. an evolving pet that grows new voxels, a weapon that gains decorative inscriptions on level up). Indexers SHOULD expose the latest payload by following the update chain per REP-3001.

## Backwards Compatibility

This extension is purely additive to REP-3005. Existing `game_item_v1` Glyphs without `voxel_payload` remain valid and require no migration. Indexers and wallets that do not implement REP-3017 SHOULD continue to surface the REP-3005 `preview` thumbnail and ignore `voxel_payload` silently.

Future versions (`voxel_payload.version: 2+`) SHOULD:

- Be defined in a separate REP
- Preserve the `version` discriminator so older clients can detect and skip unsupported payloads
- Document the migration path

## Rationale

**Why sparse voxel arrays, not dense?** Most items and builds are mostly empty space (a sword has maybe 8 voxels; a 32³ structure may have only ~1,500 filled voxels). A sparse list keeps payloads small and CBOR-friendly. Dense voxel grids are denormalized at render time by the client.

**Why a 64³ bounds cap?** Keeps inline payloads viable at the fee floor and avoids accidental mega-payloads that would be uneconomic to mint. Larger creations are expected to compose multiple Glyphs (e.g. a plot's contents as a container of payloads).

**Why a block palette and not raw block ids?** Cross-game portability. A sword inscribed with `1=rxd.stock:glass` renders correctly in any Glyph-aware game even if that game uses different internal numeric ids.

**Why allow external storage?** Some builds (entire houses, vehicles, plot exports) will exceed 4 KB. Forcing inline would either cap creator expression or burn excessive RXD on mint fees. External storage with content-hash binding preserves verifiability.

**Why tint instead of full per-voxel color?** Most use cases are recoloring shared materials (a blue version of stone, a red version of wood) rather than authoring novel materials. Tint is one extra uint per voxel; novel materials get a `textures[]` ref.

## Security Considerations

- `voxels.length` and `bounds.{w,h,d}` are bounded to prevent decompression-bomb-style attacks where an indexer or renderer is forced to materialize gigabytes from a tiny declaration
- `block_palette` values are length-limited (96 bytes) to prevent payload bloat via long name strings
- External `voxel_payload` references MUST include `hash` so clients can verify the dereferenced content; clients MUST refuse to render payloads whose hash does not match
- `meta` values are sized small (32 bytes × 8 keys per voxel) to limit per-voxel storage abuse
- Renderers SHOULD impose a runtime budget (e.g. cap total displayed voxels per scene, LOD distant items) — the protocol cap protects per-item, not per-scene
