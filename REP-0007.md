## Abstract

This REP describes `OP_REFSUPPLY`, a script opcode that would read the **global net-live circulating supply** of a Glyph reference (ref) — the total `nValue` summed over all live UTXOs bearing that ref across the entire chainstate — and push it onto the stack. This is the one read that proportional-share covenants (Uniswap-style AMM LP shares, proportional lending, rebasing tokens) cannot perform today: a covenant can only see refs it co-spends, so any formula needing the global supply `S` (e.g. LP shares `shares = dR·S/R`) is gameable by a spender who chooses which of their own UTXOs to include.

`OP_REFSUPPLY` is **not** a pure opcode addition. Radiant's ref opcodes read only transaction-local and input-UTXO data; the chainstate UTXO set is keyed by outpoint only, holds no ref-keyed aggregate, and cannot be iterated. Serving the opcode therefore requires a **new consensus-critical, ref-keyed supply index** maintained at every block connect/disconnect with exact reorg rollback. This document specifies both parts and is explicit that the index — not the opcode — is the load-bearing, high-risk change.

**This REP is OPTIONAL and is a composability upgrade, not a safety fix.** Radiant's shipped delta/conservation model (REP-3016 induction proofs, the `OP_REFVALUESUM_*` family) already lets covenants enforce per-transaction conservation without absolute supply, and **RadiantMM's RPL-LP delivers a trustless multi-LP pool today, without this primitive.** The only marginal capability `OP_REFSUPPLY` adds over fully-built-out RPL-LP is **secondary-market tradeability of LP positions as a freely-transferable fungible token**, plus removal of the one-liquidity-op-per-block singleton bottleneck — and even that does not strictly dominate RPL-LP, because it trades the singleton bottleneck for a new same-block external-mint/burn griefing class that delta-model covenants do not have. Its status is **Deferred** pending a concrete application that strictly requires this capability (see Trigger Condition).

## Status, Scope, and Trigger Condition

This REP is published as **Deferred**, not on a path to activation, by its own decision rule. It MUST NOT advance to `Draft`-on-a-path-to-implementation or any active status until **all** of the following hold:

1. **A concrete, currently-blocked Radiant application is identified** that strictly requires freely-transferable fungible proportional shares **and** cannot be served by fully-built-out RPL-LP (the `min()`-credit + 128-bit limb-math design of `RadiantMM/docs/LP-SHARE-COVENANT-DESIGN.md` §7, §11.3). No such application exists in the Radiant ecosystem as of this writing; "it would be nicer" is not a trigger.
2. **The consensus-mechanics blockers in this document are resolved with running code** — specifically the read-semantics definition compatible with the parallel check-queue (Security Considerations §"Determinism"), the limited/PSBT-context behavior, the committed-root reorg rollback, and a demonstrated fungible-LP covenant that someone actually wants.
3. **The lighter alternatives are shown insufficient** — in particular the transferable supply-certificate singleton (Rationale, Alternative 2b), which recovers much of the fungibility goal with **zero** consensus change.

Until those conditions are met, the recommended ecosystem path is **non-activation**: use RPL-LP (singleton controller) or, where an oracle trust assumption is acceptable, the non-consensus RXinDexer supply path (Alternative 4). If a prototype is nonetheless warranted, the recommended first step is the **uncommitted index behind a flag on regtest/testnet only** (Recommended Path, below) — never the maximal committed hard-fork form first.

## Specification

> The opcode shell below is buildable. The index it depends on is **not** buildable as a drop-in at the layer the earlier draft of this REP proposed; the corrected design is given in "The Committed Per-Ref Supply Index" and in Security Considerations. Read those before treating this as implementable.

### Opcode Definition

```
OP_REFSUPPLY (0xf0)

Stack: [<ref>]
Input:  <ref>            (36-byte reference identifier)
Output: <supply>         the global net-live circulating supply of <ref>,
                         encoded as a CScriptNum byte vector (see below)
```

`0xf0` is the correct value: `OP_K12 = 0xef` is the last defined opcode (`script/script.h:312`), so `FIRST_UNDEFINED_OP_VALUE` auto-increments to `0xf0` (`script/script.h:315`). Bytes `0xf0`–`0xfe` are free; `OP_REFSUPPLY` claims the first.

### Operand Format

The single operand popped from the stack is a **36-byte reference identifier**, identical in layout to the operand consumed by `OP_PUSHINPUTREF` and the `OP_REFVALUESUM_*` family: a 32-byte transaction id concatenated with a 4-byte little-endian output index, parsed via the same `uint288` blob path used by `GetPushRefs`. The opcode MUST fail with `SCRIPT_ERR_INVALID_REF_OPERAND` if the operand is not exactly 36 bytes.

The opcode does **not** require the ref to be present in the spending transaction. Unlike `OP_PUSHINPUTREF` (which only size-checks and pushes; membership is enforced elsewhere), `OP_REFSUPPLY` deliberately reads a ref that may be entirely outside the spending transaction. **This is the defining new capability and the defining new risk** (see Security Considerations).

### Value Model — what a ref's "supply" is

**Correction from the earlier draft.** A ref's on-chain "value" in this codebase is **summed `nValue` (photons/satoshis) over the live UTXOs bearing the ref** — exactly the quantity `OP_REFVALUESUM_UTXOS`/`_OUTPUTS` already sum tx-locally. There is **no** separate per-ref "token base-unit" field in consensus. Consequently:

- A ref's net-live supply is bounded above by the total photons that can carry that ref, i.e. it cannot exceed `MAX_MONEY`-scale photon totals (well under 2^63). The earlier draft's "a fungible token may set a supply of 10^18 base units, exceeding `MAX_MONEY`" framing was **incorrect** and is withdrawn: this opcode reports summed `nValue`, not an abstract token-unit count. Token issuers who want a logical unit count distinct from photon count must continue to use a decimals/divisor convention applied off this primitive — `OP_REFSUPPLY` does not expose that quantity.
- If a future REP introduces a genuinely separate per-ref token-amount field, the encoding and cost analysis here MUST be re-scoped around that new quantity; this REP does not assume one.

### Return-Value Encoding

`OP_REFSUPPLY` pushes the supply using the **same `CScriptNum` serialization the ref-sum opcodes already use** — `CScriptNum::fromInt(supply).getvch()` — so consumers handle it identically to an `OP_REFVALUESUM_UTXOS` result. The value is a signed `CScriptNum` in the documented 64-bit range `[INT64_MIN + 1, INT64_MAX]`; supply is non-negative by construction.

- If the accumulated supply would exceed `INT64_MAX` (`2^63 - 1`), the opcode MUST fail the script with `SCRIPT_ERR_REFSUPPLY_OVERFLOW` — a hard, deterministic failure, **not** a saturating cap. A silent cap would let a covenant misprice against a wrong supply. Because the supply is summed `nValue`, in practice this ceiling is only reachable by pathological photon totals; nonetheless the check is mandatory for determinism.
- A covenant doing arithmetic on the result is subject to the **same `CScriptNum`/`safeMul` 64-bit overflow rules as all Radiant arithmetic** (`OP_MUL` fails with `INVALID_NUMBER_RANGE_64_BIT` on int64 overflow — `script/interpreter.cpp:1056`). This is the dominant practical limit and is addressed in the worked example below. The opcode itself never truncates; it either pushes the exact `CScriptNum` bytes or hard-fails.

The earlier draft's "plain unsigned LE uint64, never a `CScriptNum`" wording is **withdrawn**: a bespoke unsigned codec would diverge from every existing ref-sum opcode and force covenants to special-case `OP_REFSUPPLY` results. Reusing `CScriptNum` is the only encoding consistent with the rest of the introspection family.

### The Committed Per-Ref Supply Index (the load-bearing change)

`OP_REFSUPPLY` has **no existing data structure to read.** The chainstate is keyed by outpoint only — `Coin = {CTxOut, nHeightAndIsCoinBase}`, `CCoinsMap = unordered_map<COutPoint, CCoinsCacheEntry>` — and `CCoinsViewCache::Cursor()` throws "cursor iteration not supported." The execution context loads coins only for the spending tx's own inputs. The existing `OP_REFVALUESUM_UTXOS`/`_OUTPUTS` opcodes sum **only over this tx's inputs and outputs**. There is no chain-wide aggregate, by deliberate design. This REP would add the first one.

**Data structure.** A ref-keyed aggregate persisted alongside the coin DB. Key prefix `'S'` is verified free in `txdb.cpp` (existing prefixes: `'C'`/`'c'` coins, `'B'`/`'H'` best/head blocks, `'F'`/`'R'` flags, `'b'`/`'f'`/`'l'` block index/files/last). Before implementation, **all** prefix users MUST be re-audited, including any future keys in `src/index/swapindex.cpp`, since a same-DB prefix collision is silent corruption.

```
DB_REFSUPPLY = 'S'

key   = ('S', refId[36])
value = RefSupplyEntry {
            int64   totalAmount;   // sum of nValue over all live UTXOs bearing refId
            uint64  utxoCount;     // number of live UTXOs bearing refId (for a _COUNT variant)
        }
```

`OP_REFSUPPLY` reads `totalAmount` via the **confirmed chainstate DB index** in O(1) (a single keyed lookup). Crucially, the read path is the persistent `CCoinsViewDB` index, **never** a layered mempool/dummy cache (see Maintenance and Determinism below).

**Maintenance — at the confirmed-flush layer, NOT at cache mutation.** The earlier draft proposed hooking `CCoinsViewCache::AddCoin`/`SpendCoin`. That is the **wrong layer** and would corrupt the index: `AddCoin`/`SpendCoin` (`coins.cpp:102`, `:145`) run in many non-consensus contexts — mempool acceptance, PSBT, tests, throwaway dummy caches — feeding unconfirmed and fixture coins into a supposedly confirmed aggregate. The corrected design maintains the index **only on confirmed chainstate transitions**:

- Index deltas are derived during `ConnectBlock`/`DisconnectBlock` and committed at the chainstate **flush**, not at cache mutation. Concretely, deltas are staged from the block's coin transitions (parsing each affected `scriptPubKey` via the existing `GetPushRefs`, reusing the ref summaries already computed in `ScriptExecutionContext` during validation where available) and written when chainstate flushes to disk.
- **A regression test MUST assert that mempool acceptance, PSBT construction, and dummy/test caches never mutate any `'S'` key.**
- For each ref in a newly-confirmed output: `totalAmount += nValue`, `utxoCount += 1`. For each ref in a newly-spent coin: `totalAmount -= nValue`, `utxoCount -= 1`. The index tracks **net live supply**, so a mint-then-burn nets to zero with no special casing.

**Atomicity / crash recovery — the "same WriteBatch" guarantee is false and is withdrawn.** The earlier draft mandated that supply deltas "commit in the same `WriteBatch` as the coins; a partial flush is a consensus fault." This contradicts how `CCoinsViewDB::BatchWrite` actually flushes (`txdb.cpp:104`): large blocks/reorgs are split into **multiple non-atomic** `db.WriteBatch(batch)` calls inside the loop whenever `SizeEstimate() > batch_size`, with a `DB_HEAD_BLOCKS` reconciliation marker for crash recovery (and an `_Exit(0)` crash-simulation mid-loop). There is no single all-or-nothing batch covering coins. The corrected requirement: **the supply index MUST be reconstructible/idempotent against the same `DB_HEAD_BLOCKS` recovery protocol the coins already use** — e.g. on an inconsistent shutdown the index is rebuilt from `DB_COIN`, or a supply-consistency marker is folded into the `DB_HEAD_BLOCKS` reconciliation so a half-applied flush is detected and replayed. A design that assumes atomic coins+supply commit is incorrect on this code path.

**Reorg handling — flat index.** On `DisconnectBlock`, the per-ref deltas of every tx in the disconnected block MUST be reversed exactly. The flat index supports re-derivation from the block + the existing `CBlockUndo` (which restores spent `Coin`s, giving their `scriptPubKey` and `nValue`), adding new code on the disconnect path but **no new undo data**. This covers the **flat** index only — the committed-root rollback is a separate, harder problem (below).

**Interaction with ref induction and `OP_REFVALUESUM`.** The induction rule (`validateTransactionReferenceOperations`) is a deliberate set-subset check that enforces no conservation/cardinality/supply; supply is delegated to covenants. `OP_REFSUPPLY` does not alter that rule — induction continues to govern *which refs may appear*; `OP_REFSUPPLY` merely *reports a total* over the induction-validated UTXO set. `OP_REFVALUESUM_UTXOS`/`_OUTPUTS` remain the tx-local primitives; `OP_REFSUPPLY` is their global counterpart.

### Activation

> Activation is **operationally a coordinated hard fork plus a mandatory network-wide chainstate reindex** — see Backwards Compatibility. The "soft-fork-shaped" framing applies only to the opcode bytecode in isolation (undefined → defined) and is not the operational reality.

- **Flag bit (corrected): `SCRIPT_GLOBAL_REF_SUPPLY = 1U << 29`.** The earlier draft's `1U << 27` is **already taken** by `SCRIPT_PUSH_TX_STATE` (the REP-3016 flag this document itself depends on — `script/script_flags.h:128`), and `1U << 28` is `SCRIPT_SECURITY_UPGRADE` (`script_flags.h:135`). Reusing bit 27 would alias two distinct consensus features — a direct consensus fault. The first genuinely free bit is `1U << 29`.
- Add an activation height `globalRefSupplyUpgradeHeight` in `consensus/params.h`, set per-network in `chainparams.cpp`, gated in `GetNextBlockScriptFlags` (`validation.cpp:~1770`) following the existing ER/PushTXState/SecurityUpgrade height pattern. The mainnet floor MUST be chosen on this feature's own terms — it MUST NOT borrow the legitimacy of the block-440000 `SCRIPT_SECURITY_UPGRADE` (a money-layer security fix the whole network must take); this is an optional convenience.
- Gate `OP_REFSUPPLY` in `IsOpcodeDisabled`: before activation it is an undefined/disabled opcode and MUST fail any script that executes it; after activation it dispatches to the handler.
- **Refuse-to-activate-without-index gate (normative):** a node MUST refuse to validate any block at or after `globalRefSupplyUpgradeHeight` unless it has a fully-built, height-consistent supply index. A node that reaches the fork height without the index MUST halt rather than compute wrong supplies and silently fork.

### Worked Covenant Example — Uniswap-style LP shares (and why the opcode alone does not unblock it)

The motivating formula mints LP shares on a deposit of `dR` reserve tokens into a pool holding `R` reserve with `S` shares outstanding:

```
sharesToMint = dR * S / R
```

`R` and `dR` are co-spent / tx-local and already expressible via `OP_REFVALUESUM_UTXOS` and the deposit output delta. The blocker is `S` — the global LP-share supply — which `OP_REFSUPPLY` would authenticate unforgeably:

```
// pseudocode for the LP-mint covenant predicate
<lpRef>            OP_REFSUPPLY         // S  = global LP-share supply (NEW, unforgeable)
<poolReserveRef>   OP_REFVALUESUM_UTXOS // R  = reserve co-spent by pool input
                   ...                   // dR from the deposit output delta
// the proportional check, cross-multiplied to avoid division:
//   require: sharesMintedOut * R == dR * S
```

**Critical caveat the earlier draft omitted.** The cross-multiplied check computes `dR * S` (and `sharesMintedOut * R`) with `OP_MUL`, which uses `safeMul` and **hard-fails with `INVALID_NUMBER_RANGE_64_BIT` on int64 overflow** (`interpreter.cpp:1056`). `dR * S` overflows int64 whenever the deposit `dR` and the global supply `S` are both moderately large — i.e. **precisely the fungible-large-supply case this REP exists to enable.** Therefore:

- `OP_REFSUPPLY` alone does **not** unblock fungible proportional shares at scale. A covenant must additionally either (a) operate in a slippage-bounded regime where `dR`, `R`, `S` are provably small enough that all intermediate products fit int64 — which caps pool/position sizes and re-introduces a bound similar to RPL-LP's — or (b) rely on a wider-than-64-bit big-integer arithmetic primitive that Radiant does **not** currently have. RadiantMM's RPL-LP already carries 128-bit limb math (`LP-SHARE-COVENANT-DESIGN.md` §7) precisely to dodge this; `OP_REFSUPPLY` would need the same companion primitive to be useful at scale.
- This is a material finding that **undercuts the Motivation's implicit "this single opcode unblocks Uniswap-on-UTXO" claim.** The honest statement is: `OP_REFSUPPLY` removes the *global-supply-read* blocker, but the *64-bit arithmetic* blocker remains and would require its own separate work.

Under the status-quo approximation `tx.inputs.refValueSum($lpRef)`, a spender *sets* `S` by choosing which of their own LP UTXOs to include — an unbounded reserve drain on `remove` and a brick (`S = 0`) on honest `add` (`LP-SHARE-COVENANT-DESIGN.md` §0, §11, §14). `OP_REFSUPPLY` closes *that* hole; it does not by itself deliver arbitrary-scale fungible shares.

## Motivation

RadiantMM's LP-share design makes the gap concrete. Radiant covenants can observe co-spent value and ref deltas but cannot read a ref's global circulating supply. RadiantMM's v3 attempt to mint fungible Uniswap-style LP shares ran into this: every proportional formula needs the global LP supply `S`, and the only available approximation, `tx.inputs.refValueSum($lpRef)`, sums only co-spent inputs — so a spender *sets* `S`, yielding an unbounded reserve drain on remove and a brick on honest add.

The shipped RPL-LP design (`RadiantMM/docs/LP-SHARE-COVENANT-DESIGN.md` §0, §11, §14) sidesteps this by abandoning fungible proportional shares for a single stateful controller that acts as its own authenticated supply bookkeeper — **trustless, multi-LP, and shipping today**, but explicitly **not** Uniswap-fungible and historically bounded (the §7 128-bit-limb / §11.3 `min()`-credit work removes the exact-ratio cliff and the ~0.95 RXD leg cap, leaving only the "shares aren't free-floating tokens" property).

**The honest delta.** `OP_REFSUPPLY` does **not** add trustlessness, safety, conservation, or bounded-pool functionality — RPL-LP already has all of those. Its marginal capability over fully-built-out RPL-LP is exactly two things:

1. **Secondary-market tradeability of LP positions as a freely-transferable fungible token** (vs. a position redeemable at the controller). Nothing in the Radiant ecosystem currently demands a secondary LP-token market.
2. **Removal of the one-liquidity-op-per-block singleton bottleneck** (`LP-SHARE-COVENANT-DESIGN.md` §11.4).

And it does **not** strictly dominate RPL-LP even on fungibility: RPL-LP reads its in-controller `shareTotal`, immune to external mint/burn; an `OP_REFSUPPLY` covenant reads global supply that **any third party can move**, introducing a same-block griefing class RPL-LP lacks (Security Considerations). This is a lateral move on a tradeoff surface, not an unambiguous upgrade.

So the trigger condition is not met: no concrete, currently-blocked application requires free-floating fungible proportional shares. By this REP's own decision rule the proposal resolves to **non-activation**, which is why its status is **Deferred**.

## Rationale

### Why a global read at all, when no UTXO chain has one?

A survey of prior art is unambiguous: **no UTXO system exposes an absolute global-supply read to script.** Bitcoin enforces supply only implicitly via the per-tx `sum(in) >= sum(out) + fee` rule. Every Bitcoin covenant proposal — CTV/BIP-119, OP_VAULT/BIP-345, MATT/`OP_CHECKCONTRACTVERIFY`/BIP-443 — restricts introspection to the spending transaction's own inputs/outputs; cumulative quantities must be threaded through inputs/outputs (the state-machine pattern). Cardano native assets constrain the `mint` field + preservation-of-value (a delta), never a supply read; a Cardano project needing a cap builds an application-level committed registry whose own README states the ledger "lacks native on-chain visibility into an asset's total supply." Grin/MimbleWimble proves no-inflation by commitment-sum conservation with no stored `totalSupply`. Liquid/Elements gates issuance/reissuance + balancing, with no script-readable per-asset supply.

The **only** system where global supply is a first-class read is Ethereum (`ERC20.totalSupply` is a single `SLOAD`) — precisely because Ethereum has shared mutable global contract state. "Global supply read" and "account-model shared state" are the same coin: you cannot have the read without re-introducing global mutable state, or a committed index that simulates it. This REP's central honest admission is that `OP_REFSUPPLY` **re-imports the exact property UTXO designs were built to avoid** — and it would be Radiant's **first** global mutable consensus aggregate. That cost is paid against a benefit with, at present, **zero must-have consumers**.

### Alternative Approaches Considered

1. **Do nothing; use delta + induction (REP-3016).** Strongly precedented, zero consensus risk, already shipped. Suffices for conservation, caps-via-singleton, and RPL-LP-style pools. Cannot express fungible proportional shares in O(1) without a singleton controller — but that limitation has no demonstrated consumer. **This is the recommended status-quo path.**

2. **Application-level committed index (singleton state-thread) — RPL-LP, the shipping design.** A covenant maintains its own authenticated supply counter in a singleton UTXO threaded forward (`LP-SHARE-COVENANT-DESIGN.md` §2, §4: `shareTotal` in controller state, delta-pinned on every hop). **No consensus change.** Its `shareTotal` *is* an authenticated in-band supply certificate, and it is immune to external mint/burn griefing. The only deficiency vs. `OP_REFSUPPLY` is that the share is not freely transferable and operations serialize (one liquidity op per block).

   **2b. Transferable / sharded supply certificate (under-credited lighter alternative — deserves the fairest treatment).** The certificate need not be a bottleneck: a *transferable* supply certificate — a singleton NFT whose state **is** the authenticated supply, which holders reference **read-only via co-spend** — recovers much of the fungibility goal with **zero consensus change**. The serialization limit (§11.4) is attackable by batching multiple liquidity ops per certificate-update, or by a **sharded certificate** design (N sub-certificates summing to the total, each updatable independently, reconciled periodically). Before paying for a consensus fork, this REP requires a demonstration that a transferable/sharded certificate **cannot** close the fungibility gap at lower cost. It very plausibly can. This is the strongest argument against `OP_REFSUPPLY` ever activating.

3. **`OP_REFVALUESUM_UTXOS` as a proxy for `S`.** The status-quo hack. **Rejected: unsound** — spender controls the co-spend set, drains/bricks the pool.

4. **Off-chain oracle (RXinDexer supply).** **Corrected characterization:** RXinDexer's `get_token_supply` (`glyph_index.py:2472`) computes circulating supply by **iterating the `HOLDER_BY_REF` prefix and summing every holder balance — O(holders), not O(1)** as the earlier draft claimed. Separately, the stored `GS`/`SUPPLY` key (`glyph_index.py:52`) tracks **minted** supply (`current_supply` = premine + mined deltas, `glyph_index.py:1074`), **not** net-live circulating supply after burns/spends. This cuts both ways: (a) the oracle alternative is somewhat more expensive than implied (a scan, not a stored read), but (b) it proves the exact **net-live ref supply** quantity is genuinely **novel even off-chain**, which strengthens the "this is a real, deep new requirement" point while weakening any "RXinDexer already has it, just sign it" framing. A signed-oracle covenant remains a pragmatic non-consensus alternative that needs no fork, at the cost of an oracle trust assumption the rest of the AMM avoids. **Recommended over a fork where that trust assumption is tolerable.**

5. **Uncommitted consensus index (no header commitment).** Cheapest consensus form: maintain the `'S'+ref` index in chainstate but do not commit a root to the header. Cheaper, but **consensus-critical yet unverifiable** — two implementations (or a node with a parse/rollback bug) can **silently** disagree on supply with no header check to catch it, and SPV clients cannot verify the value at all. Unsafe for mainnet. **However, it is the correct minimum-viable *prototype* form on regtest/testnet** (see Recommended Path).

6. **`OP_REFSUPPLY` + committed index — the only mainnet-safe form, and a HARD FORK.** The index plus a rolling commitment (Merkle/MMR root over `ref → supply`) folded into the block header or a coinbase commitment. Every node verifies identical totals; SPV/light verification becomes possible; a divergence becomes a loud validation failure instead of a silent split. This is the **only split-safe, light-verifiable form** — and it requires a new block-validity rule (a header/coinbase field rejecting old-format blocks), i.e. **a hard fork, not the soft-fork-shaped opcode addition the earlier framing leaned on.** Its reorg story is **unsolved and is the actual hard part**: a Merkle/MMR root cannot be cheaply re-derived on `DisconnectBlock` from `CBlockUndo` alone (that re-derivation only works for the *flat* index). It requires either storing per-block root pre-image deltas in `CBlockUndo` (accepting the cost the earlier draft tried to reject) or an MMR with O(log n) rollback proofs. **Note:** this Radiant-Node tree has **no `coinstatsindex` and no MuHash** (`src/index/` holds only `base`, `swapindex`, `txindex`) — there is **no** existing rolling-UTXO-commitment machinery to extend, so the entire authenticated-map subsystem is greenfield consensus code. If `OP_REFSUPPLY` ever ships to mainnet it MUST be in this form; it must NOT ship uncommitted.

### Recommended Path (sequencing)

The earlier draft recommended the maximal-cost committed form as primary while simultaneously recommending against activation — internally inconsistent. Corrected sequencing, matching the optionality stance:

1. **Default: do nothing.** Use RPL-LP, or the RXinDexer signed-oracle path where an oracle is acceptable. (Alternatives 1, 2, 4.)
2. **If fungibility is genuinely wanted, first build the transferable/sharded supply certificate** (Alternative 2b) — zero consensus change — and prove it insufficient before considering any fork.
3. **Only if 1–2 fail and a real consumer exists:** prototype the **uncommitted index behind a flag on regtest/testnet** (Alternative 5) and demonstrate a fungible-LP covenant someone actually wants, including the 64-bit-arithmetic companion primitive the worked example shows is also needed.
4. **Only after a proven, wanted prototype:** debate paying for the **committed hard-fork form** (Alternative 6), resolving the committed-root reorg rollback first.

### Why bytes-via-CScriptNum and fail-on-overflow

Determinism: every node computes the identical exact integer and takes the identical branch (push-exact vs. hard-fail). Reusing `CScriptNum` keeps the result consistent with the existing ref-sum family; a bespoke unsigned codec would force covenants to special-case the result. A saturating cap would let covenants silently misprice; failing on `> INT64_MAX` keeps the opcode total and unambiguous. The fail-on-overflow choice carries a griefing hazard (see Security Considerations).

### Why this is framed as optional

Because it is. The delta/induction model is the precedented, lower-risk design, sufficient for safety and for the pools Radiant ships today. This REP exists to enable a *new class of covenant* (fungible proportional shares) that no current application requires, at the cost of the first global mutable aggregate in Radiant consensus and a coordinated hard fork. If singleton-controller pools (RPL-LP) or a transferable certificate are acceptable — and nothing suggests otherwise — **the correct decision is non-activation.**

## Backwards Compatibility

**Opcode in isolation: soft-fork-shaped, but operationally a coordinated fork.** `0xf0` is currently undefined; a script executing it fails. Defining `OP_REFSUPPLY` only *adds* a way for previously-invalid scripts to become valid after activation — soft-fork-shaped in the narrow bytecode sense. But old, un-upgraded nodes reject blocks containing accepted `OP_REFSUPPLY` spends and fork off, so **all nodes must upgrade before activation** — operationally a coordinated fork, not a silently-deployable soft fork. The committed-index form (the only mainnet-safe form) adds a header/coinbase rule and is a **true hard fork**.

**Index: mandatory reindex / backfill — the real compatibility cost.** The supply index is a function of the *entire historical UTXO set*. A node cannot serve correct `OP_REFSUPPLY` values at the fork height unless it has already built `'S'+ref → supply` over all live coins. Therefore:

- Upgrading nodes MUST perform a one-time backfill: iterate the existing UTXO set once, parse refs from each `scriptPubKey`, accumulate the index. Comparable to `-reindex-chainstate` in duration and **mandatory**; the refuse-to-activate-without-index gate enforces it.
- **Backfill determinism is normative:** all implementations MUST use a canonical iteration/accumulation order so they compute an **identical** index (and, in the committed form, an identical root) at activation. A byte-for-byte disagreement at activation is a chain split.
- **assumeutxo / fast-sync nodes cannot derive the index from a snapshot** (they never built the full UTXO set locally). This sync path MUST be explicitly excluded from validating past the fork height, or the snapshot format MUST be extended to carry the index — an additional cost the snapshot machinery does not currently bear.
- New nodes building chainstate from scratch (IBD) accumulate the index incrementally during sync, at the per-output `GetPushRefs` cost noted in Security Considerations.

**Existing opcodes unchanged.** `OP_REFVALUESUM_*`, induction (`validateTransactionReferenceOperations`), and all REP-3016 primitives are untouched. No existing covenant changes behavior.

## Security Considerations

### Determinism — supply as-of which moment? (corrected; the earlier definition was unrealizable)

The earlier draft defined the read as "supply as of the start of the block, including the cumulative effects of all earlier transactions in that block but excluding the executing transaction's own effects." **This is physically unrealizable on Radiant's `ConnectBlock`.** All outputs of all block txs are `AddCoins`'d in one pass up front (`validation.cpp:1991`–`1995`) before any script runs; spends happen later; script checks run in **parallel** on a 128-thread queue (`:1712`, `:1987`). At script time the index would reflect the whole block's mints but none of its spends, and under parallel checks there is no deterministic "earlier txs in this block" ordering at all.

**Corrected definition:** `OP_REFSUPPLY` reads **confirmed supply as of the parent block's tip** — i.e. excluding **all** effects of the block currently being connected. This is the only value that is (a) deterministic, (b) identical in mempool acceptance and in block validation, (c) compatible with the up-front `AddCoins` pass and the parallel check-queue, and (d) free of the circular dependency where a tx's validity depends on its own not-yet-applied delta. It also **eliminates the mempool-vs-block divergence** the earlier draft created (where the same tx would read tip-with-spends in mempool but all-block-mints-no-spends in a block). Mempool acceptance reads the same confirmed parent-tip index; mempool contents are never read (per-node mempool differences would make validity non-deterministic — a fatal consensus flaw and DoS vector).

If intra-block effects were ever required, `ConnectBlock` would have to be re-architected (per-tx-position snapshots, serialized checks for `OP_REFSUPPLY` txs), at a throughput cost. The parent-tip definition is strongly preferred and is what this REP specifies.

### The index is consensus-critical — a bug forks the chain

The index becomes part of the consensus state machine. A parse bug, a reorg off-by-one, or a `DB_HEAD_BLOCKS`-recovery edge mishandled produces a wrong supply → a different `OP_REFSUPPLY` result → nodes disagree on validity → **a chain split.** This is strictly more dangerous than a normal opcode bug (which affects only scripts that use it): an index bug affects every node's view of every ref's supply. In the **uncommitted** form the divergence is **silent** (no header check catches it); the **committed** form converts a silent split into a loud, detectable validation failure — the principal argument for paying the committed-index cost, and the reason the uncommitted form is **prototype-only, never mainnet.**

### SPV / light-client impact

`OP_REFSUPPLY` makes script validity depend on a global aggregate an SPV client cannot check. In the uncommitted form a light client simply cannot verify an `OP_REFSUPPLY`-dependent spend. In the committed form a light client can verify the supply against the header commitment with a Merkle/MMR proof. Combined with the limited-context hard-fail above: **any covenant wallets must validate client-side (e.g. RadiantMM share minting) effectively requires the committed form plus a supply proof** to remain light-client-friendly.

### Reorg consistency

Supply is height-defined and MUST roll back exactly on `DisconnectBlock`. For the **flat** index, re-derivation from block + `CBlockUndo` keeps a single source of truth. For the **committed** root the rollback is unsolved by re-derivation and requires per-block root deltas in `CBlockUndo` or an MMR — the actual hard part of the committed form. Deep reorgs touching many refs must roll back all affected `'S'` keys consistently with the coins under the same `DB_HEAD_BLOCKS` recovery protocol.

### Validation cost / DoS — bounds are NORMATIVE, not advisory

- **Per-output ref-parse on the write path.** Confirmed coin transitions run `GetPushRefs` per affected output. During block connect this SHOULD reuse the ref summaries already in `ScriptExecutionContext`. But **IBD `AddCoins` and other paths run without a full context** and would re-parse — new per-output CPU on the hottest validation path (today the write path only checks `IsUnspendable`, `coins.cpp:105`). The per-block ref-parse cost MUST be quantified (GetPushRefs invocations per block / per UTXO at backfill) and bounded inside the existing per-block validation budget (cf. the V2-fork O(1) 128 MB guard). No claim of "O(1)/bounded" is acceptable without numbers.
- **Unbounded distinct-ref keyspace.** The index grows with the number of distinct refs ever minted — unbounded — a DoS and state-bloat surface, and (committed form) an authenticated map over an unbounded keyset. The earlier draft deferred this to "a cap MAY be required." For a consensus structure this MUST be normative: a per-block cap on newly-created distinct refs and/or total index growth MUST be specified **as consensus**, because changing the cap later is itself a fork.
- **Opcode execution cost.** The read is O(1) (single keyed lookup); the cost is entirely in index maintenance.

### Out-of-tx reactivity — a genuine new threat class, requiring a committed supply-assumption witness

Today a covenant's outcome is a function of **only its own transaction and the coins it spends** (`CheckInputs` passes "only things clearly committed to by tx's hash"). `OP_REFSUPPLY` breaks that: a covenant can react to global state mutated by **unrelated third parties**. Consequences:

- **Loss of validation isolation.** Parallel script validation, the limited-context optimization, and PSBT/offline signing all assume a script validates from tx + input-coins alone. A global read breaks that; the limited context has no answer and must hard-fail (above).
- **Same-block griefing — worse than AMM slippage.** Because (per Determinism) the read is parent-tip, an attacker cannot move the value *within* the victim's block — but across blocks, a third party's mint/burn between a victim's signing and inclusion can re-price or invalidate the covenant. Unlike AMM price slippage (bounded by capital), ref mint/burn can be near-free. **RPL-LP does not have this vector** (it reads in-controller `shareTotal`, immune to external mint/burn) — so `OP_REFSUPPLY` does not dominate RPL-LP even on fungibility; it trades the singleton bottleneck for this exposure.
- **Mitigation (normative):** `OP_REFSUPPLY` covenants MUST bind a **spender-committed supply assumption** — a `max-S` (or `S`-band / `S`-delta) witness in the covenant — so a covenant cannot be silently re-priced outside the spender's intended band by external mint/burn. Tolerance bands alone (as AMMs use for price) are insufficient because the underlying quantity is externally and cheaply mutable; the spender MUST commit to the supply assumption explicitly.
- **Pre-signed-tx staleness.** A pre-signed tx reading `OP_REFSUPPLY` may become invalid between signing and broadcast if supply changes — unlike delta covenants, which are stable against external state. The supply-assumption witness bounds, but does not eliminate, this.

### Overflow semantics create a permanent-brick griefing vector (acknowledged hazard)

Because supply is summed over **all** live UTXOs and any third party can mint more of a ref, an adversary (or honest growth) can push a ref's total past `INT64_MAX` and **permanently brick every `OP_REFSUPPLY` covenant referencing it** — hard-fail forever, since supply can only fall via burns the attacker won't perform. The "use decimals" advice does not help an already-deployed covenant. This is a real covenant-design hazard specific to the fail-on-overflow choice (chosen over a cap for determinism), and is stated here as a hazard, not framed as pure upside. In practice the photon-bounded value model (above) makes this hard to reach, but covenant authors MUST treat it as possible.

### Summary of the threat posture

`OP_REFSUPPLY` admits global mutable state into a model designed to exclude it. The costs — consensus-critical index, hard-fork-only safe form, lost validation isolation, a new external-mint/burn griefing class, an overflow brick vector, mandatory reindex, and an unsolved committed-root reorg story — are paid against a benefit (secondary-market fungible LP tokens) with **no currently-required consumer**. The recommended decision is **non-activation**, with the lighter transferable-certificate and signed-oracle paths preferred where fungibility is genuinely wanted. This REP stands as a thinking document and a parked specification, not an active standards proposal.
